# modbus-slave v2 — эмулятор Modbus RTU slave и программный датчик

[English version](README.md)

`modbus-slave` превращает последовательный порт в одно или несколько устройств Modbus RTU. Зачем это нужно:

- **проверять мастер** (SCADA, шлюз, ПЛК) без настоящих устройств: правдоподобные значения, любая скорость,
  много устройств на линии, внесение сбоев;
- **отдавать реальные данные как Modbus-устройство** («программный датчик»): значения регистров берутся из
  текстовых файлов, которые обновляет любой скрипт (I2C, 1-Wire, sysfs, температура CPU, время…);
- **проверять линию**: режим pty для тестов без железа, статистика по каждой линии.

Один статический бинарник, без зависимостей. v2 — переписанная на Go версия на C (v1, она осталась в `src/`).
Командная строка v1 продолжает работать.

> Статус: **v2 в разработке** (ветка `v2`). Linux проверен, в том числе на настоящих линиях FT4232H. Сборка
> для Windows (`COM3`, Win32 API) **проверена на Windows 11**: два FT232R, RTU против modpoll, сырой `line-test`,
> веб-страница со списком COM-портов; `.exe` версии v1 пока лежит в `bin/`. Ограничения на Windows: порты
> задаются как `COM<n>`; нет `--pty` (вместо него — пара com0com), нет номеров каналов FT4232H и `-d/-k/-s`;
> задержку FTDI настраивают в драйвере (Диспетчер устройств → порт → Дополнительно).

## Сборка

```sh
./build.sh                 # dist/modbus-slave-linux-{amd64,arm64,arm} (статические), dist/modbus-slave-windows-amd64.exe
go build ./cmd/modbus-slave
go test -race ./...
```

## Быстрый старт

```sh
# как в v1: 5 устройств на порту, случайные значения; устройство 1 — из файла
modbus-slave -p /dev/ttyUSB0 -b 115200 -a 5 -f 1:/tmp/cpu.dat -t 15

# 4 линии FT4232H, на каждой 4 датчика KTH2-R, ответ через 5 мс
modbus-slave -p 0 -p 1 -p 2 -p 3 -b 57600 --profile kth2r --units 1-4 --delay 5

# без железа: pty; мастер открывает /tmp/ttyEMU
modbus-slave --pty /tmp/ttyEMU -b 9600 --profile kth2r
mbpoll -m rtu -b 9600 -P none -a 1 -r 769 -c 2 /tmp/ttyEMU

# своё устройство из YAML-профиля и локальный API
modbus-slave -p /dev/ttyS7 -b 9600 --profile examples/soft-sensor.yaml --api 127.0.0.1:8650

# Modbus TCP вместо последовательного порта
modbus-slave --tcp :502 --profile kth2r --units 1-4
```

## Параметры

| Параметр | Что делает |
|---|---|
| `-p <порт>` | Порт: `/dev/ttyUSB0`, `/dev/ttyS7` или **канал FT4232H/FT2232H** `0..3` / `A..D`. Канал ищется по номеру USB-интерфейса, поэтому он не теряется при переподключении, когда ядро выдаёт другие имена `ttyUSB4..7`. **Повторите `-p`, чтобы обслуживать несколько линий.** |
| `--tcp <адрес>` | Отвечать по **Modbus TCP** на `:502` / `0.0.0.0:1502` вместо порта. Unit id выбирает устройство, 0 и 255 = первое, чужой адрес получает исключение 0x0B (как от шлюза). Можно повторять. |
| `--state <файл>` | Сохранять датчики, изменённые на веб-странице или через API, после перезапуска. |
| `--pty <ссылка>` | Создать pty и сделать на него ссылку `<ссылка>` (тесты без железа). Можно повторять. |
| `-b <скорость>` | Любая скорость, которую умеет UART, 1200 … 4000000 (по умолчанию 19200). |
| `-o <режим>` | `8N1` `8E1` `8O1` `7E1` `8N2` (по умолчанию `8N1`). |
| `-a <n>` / `--units 1-4,7` | Адреса устройств: `1..n` или список. На всех линиях одинаковые. |
| `--profile <p>` | `generic` (по умолчанию, устройство v1), встроенный профиль (`--list-profiles`) или YAML-файл. |
| `-f [линия.]id:файл` | `generic`: значения устройства `id` из файла; `2.1:/tmp/x` — только на линии 2. |
| `-t <с>` | Максимальный возраст файла; если файл старше, отдаются нули (по умолчанию 10, `0` — без проверки). |
| `--regs <n>` | `generic`: число регистров (по умолчанию 20). |
| `--delay`, `--jitter` | Задержка ответа и случайная добавка к ней, мс. |
| `--drop`, `--exc`, `--badcrc` | Вероятность не ответить / ответить исключением 4 / испортить CRC. |
| `--frag <n>`, `--frag-gap <мс>` | Отправить ответ `n` кусками с паузой между ними (проверка t3.5 у мастера). |
| `--echo` | Отбрасывать эхо своих ответов (приёмопередатчик слышит сам себя). |
| `--latency <мс>` | `latency_timer` FTDI (по умолчанию 1; заводские 16 мс добавляют до 16 мс к каждому ответу). |
| `--gap <мс>` | Пауза, после которой незаконченный кадр отбрасывается (по умолчанию 20; `0` — t3.5 для скорости). |
| `--report <с>` | Выводить статистику каждые `с` секунд (по умолчанию 60, `0` — выключено). |
| `--api <адрес>` | Локальный JSON API и веб-страница: `127.0.0.1:ПОРТ` или `unix:/путь`. Для адреса, доступного по сети (`0.0.0.0:8650`), нужен `--api-token` или `--api-token-file`. |
| `--seed <n>` | Зерно случайных чисел, чтобы прогоны повторялись. |
| `-d` / `-k` / `-s` | Запуск в фоне (логи в syslog) / остановка / состояние — как в v1. Под systemd лучше использовать unit. |

Конец запроса определяется по длине, которую задаёт код функции. Поэтому ответ уходит сразу после последнего
байта запроса. Битый кадр или мусор перед правильным запросом этот запрос не съедают. Если порт пропал
(выдернули USB), он откроется снова, когда появится, а устройства сохранят своё состояние.

## Значения из файлов (программный датчик)

В файле одно число на строку. Скрипт перезаписывает файл атомарно:

```sh
printf "4523\n1013\n" > /tmp/s1.tmp && mv /tmp/s1.tmp /tmp/s1.dat
```

- Нет файла — отдаются нули. Файл старше `-t` / `max_age` — тоже нули, а с `on_stale: exception` вместо них
  исключение 4. Так мастер сразу видит, что скрипт с данными упал, и не читает застывшие значения.
- Файл перечитывается только тогда, когда изменился.
- Числа могут быть отрицательными (`-5` хранится в дополнительном коде), шестнадцатеричными (`0x1F`) или дробными
  (`45.23`, если в профиле задан `scale`). Текст после числа игнорируется (`4523  # T x100`).

Готовые скрипты для данных: `scripts/cpu_temp_to_modbus.sh` и `scripts/time_to_modbus.sh`.

## Профили устройств (YAML)

В профиле перечислены коды функций и регистры. У каждого блока регистров **один источник значений**:

| Источник | Пример | Замечания |
|---|---|---|
| `value` / `values` | `{addr: 0, values: [1, 0x120]}` | константа; к ней прибавляются `base`, `line_step`, `unit_step`, `index_step` |
| `string` | `{addr: 2, string: "KTH2-R"}` | 2 символа на регистр |
| `wave` | `{addr: 0x300, wave: {shape: sine, base: 215, amp: 30, period: 600, noise: 1}}` | формы `saw`, `triangle`, `sine`, `square`, `const`; `line_step`/`unit_step` сдвигают базу |
| `file` | `{addr: 20, file: /run/s{unit}.dat, file_line: 0, max_age: 10, on_stale: exception}` | в пути можно использовать `{line}`, `{unit}` |
| `random` | `{addr: 50, count: 10, random: true}` | новые значения при каждом чтении |
| `special(s)` | `{addr: 0x1000, specials: [served_hi, served_lo, line, unit, baud100]}` | ещё `speed_code`, `parity_code`; `unit` с `rw: true` меняет адрес устройства |

Параметры блока:
- `count` — число значений;
- `type` — `uint16`, `int16`, `uint32`, `int32`, `float32`;
- `word_order` — порядок слов: `big` (старшее слово первым) или `little`;
- `scale` — в регистр записывается значение × scale;
- `rw: true` — мастер может записывать блок; запись FC 6/16 проходит целиком или не проходит вовсе;
- `add: <адрес>` — к значению прибавляется значение другого регистра, например поправка, которую пишет мастер.

`input:` — необязательная отдельная карта для FC 4; если её нет, FC 4 читает карту holding. Ошибкой считаются
неизвестные ключи, пересекающиеся регистры и два источника в одном блоке.

Встроенные профили (`internal/profile/builtin/`):
- `kth2r` — датчик температуры и влажности KTH2-R;
- `dl303` — ICP DAS DL-303 (CO/CO2/T/RH), `pm3112` — 4-канальный счётчик ICP DAS PM-3112,
  `jsy1003f` — счётчик JSY1003F: регистры как в конфигах
  [lab240/telegraf-grafana-configs](https://github.com/lab240/telegraf-grafana-configs);
- `cpu` — сама плата: синтетическая температура CPU, настоящие загрузка и аптайм из `/proc`.
Файлы из `/proc` и `/sys` перечитываются при каждом запросе.
Пример: [`examples/soft-sensor.yaml`](examples/soft-sensor.yaml) — температура CPU из файла как float32 и
int16, время работы как uint32, уставки, которые пишет мастер.

## Веб-страница и локальный JSON API

`--api 127.0.0.1:8650` (или `unix:/run/modbus-slave.sock`; любой другой адрес — только с токеном, см.
[ниже](#доступ-к-странице-с-других-компьютеров-токен)).
`http://<хост>:8650/` — веб-страница: **одна плитка на каждый эмулируемый датчик**. В плитке выбирается шаблон
(Виртуальный, KTH2-R, свои YAML-профили), адрес, **RTU или TCP**, для RTU — порт, скорость и чётность, и режим:
**нормальный** или **психованный** (медленный, иногда не отвечает, отвечает исключением или битым CRC). Изменения
применяются сразу. Датчики на одном порту — одна шина RS-485 (новая скорость или чётность ставится всем); датчики
с одним TCP-портом — один Modbus TCP сервер, unit id выбирает датчик (0 и 255 = первый, чужой адрес получает
исключение 0x0B). Кнопка ☰ показывает регистры датчика с живыми значениями и записью. В «Дополнительно» — что делает
психованный режим и шины со счётчиками. С `--state ФАЙЛ` датчики сохраняются после перезапуска (тогда порты и
адреса из командной строки — только первый запуск).

Шаблоны: `generic` (устройство v1), встроенные профили и `*.yaml` из `/etc/modbus-slave/profiles` и
`/usr/share/modbus-slave/profiles`.

| Запрос | |
|---|---|
| `GET /api/v1/status` | версия, время работы, шины (линии) со счётчиками |
| `GET /api/v1/templates` | шаблоны датчиков |
| `GET /api/v1/ports` | последовательные порты в системе (постоянные ссылки `/dev/serial/by-path`, производитель и модель USB) |
| `GET /api/v1/sensors` | датчики и их состояние (открыт, ошибка, сколько запросов, сколько секунд с последнего) |
| `POST /api/v1/sensors` | добавить: `{"profile": "kth2r", "unit": 1, "transport": "rtu", "port": "/dev/ttyUSB0", "baud": 9600, "mode": "8N1"}` |
| `PUT /api/v1/sensors/{id}` | изменить заданные поля: `{"transport": "tcp", "listen": ":502"}`, `{"crazy": true}`, `{"baud": 19200, "mode": "8E1"}` |
| `DELETE /api/v1/sensors/{id}` | удалить |
| `GET /api/v1/sensors/{id}/map` | карта регистров шаблона: блоки с названием, типом, источником, записью |
| `GET /api/v1/sensors/{id}/registers?addr=0x300&count=2[&fc=4]` | прочитать регистры |
| `PUT /api/v1/sensors/{id}/registers` | записать регистры, доступные для записи: `{"addr": 1279, "values": [-50]}` |
| `GET /api/v1/sensors?values=1` | то же и основные значения всех датчиков: один запрос на всю страницу |
| `GET /api/v1/service`, `PUT /api/v1/service` | `{"running": false}` останавливает эмуляцию (порты закрыты, страница остаётся), `{"enabled": true}` = `systemctl enable` (запуск при старте системы) |
| `GET /api/v1/crazy`, `PUT /api/v1/crazy` | сбои психованного режима: `{"delay_ms": 20, "jitter_ms": 400, "drop": 0.1, "exc": 0.05, "badcrc": 0.05, "frag": 0, "frag_gap_ms": 5}` |

```sh
curl -s localhost:8650/api/v1/sensors
curl -s -X PUT -d '{"crazy": true}' localhost:8650/api/v1/sensors/2
curl -s -X PUT -d '{"transport": "tcp", "listen": ":502"}' localhost:8650/api/v1/sensors/1
```

Регистры `speed_code`, `parity_code`, `baud100` следуют настройкам датчика. Сбои из командной строки
(`--delay`, `--drop`, ...) — это нормальный режим всех датчиков.


### Доступ к странице с других компьютеров: токен

По умолчанию страница открывается только на той же машине (`127.0.0.1`). Чтобы открыть её с другого компьютера,
слушайте на всех адресах и задайте токен, без токена программа не запустится:

```sh
# Linux
modbus-slave -p /dev/ttyUSB0 -b 9600 --profile kth2r --units 1-4 --api 0.0.0.0:8650 --api-token 678876
# Windows
.\modbus-slave.exe -p COM5 -b 9600 --profile kth2r --units 1-4 --api 0.0.0.0:8650 --api-token 678876
```

Откройте `http://<IP этой машины>:8650/`. Страница один раз попросит токен (поле вверху), введите `678876`, браузер
его запомнит. Для API токен передаётся заголовком: `curl -H 'Authorization: Bearer 678876' http://<IP>:8650/api/v1/status`.

`678876` — только пример: придумайте свой. Встроенного токена по умолчанию нет намеренно: его знали бы все.

**Как сменить токен:** перезапустите программу с другим `--api-token`. В браузере старый токен перестанет
подходить, страница снова покажет поле для токена, введите новый.

**Токен из файла** (`--api-token-file`) — то же, но токен не виден в списке процессов (`ps`, Диспетчер задач); так
сделано в пакете для плат (`/etc/modbus-slave/api.token`). Сменить: записать в файл новый токен и перезапустить:

```sh
echo 678876 > /etc/modbus-slave/api.token && systemctl restart modbus-slave
```

На Windows разрешите порт 8650 в брандмауэре (Windows спросит при первом запуске) или командой администратора:
`netsh advfirewall firewall add rule name="modbus-slave 8650" dir=in action=allow protocol=TCP localport=8650`.

## Тест линии

Сырой тест самой линии RS-485, без Modbus. Одна сторона передаёт сразу во все порты, другая слушает, потом
стороны меняются ролями. За минуту видно перепутанные и оборванные пары и предельную скорость длинной линии.

```sh
modbus-slave line-test listen -p 0 -p 1 -p 2 -p 3 -b 57600 --secs 6     # запустить первым
modbus-slave line-test send   -p 0 -p 1 -p 2 -p 3 -b 57600 --secs 3
```

`--pattern tokens` (по умолчанию) отправляет `<P1 00042>`: приёмник сообщает, с какого порта пришли данные и
сколько байт искажено. `--pattern bytes` отправляет `00..FF` и считает перевёрнутые биты. Если линия слишком
медленная для этой скорости, одиночный 0 после единиц превращается в 1 (`03` приходит как `07`). `--burst 8 --pause 20` шлёт короткие пачки с
тишиной между ними, как кадры Modbus. **Скорость проверяйте с `--pattern bytes`**: метки состоят только из цифр и
скобок и не содержат сочетаний бит, которые длинная линия портит первыми (на 915 м при 230400 метки проходили чисто,
а `C4 4F` приходило как `C4 FE`). Настоящий прогон: 915 м витой пары, 115200, без терминатора на дальнем конце:

```
  0              30730 bytes  30597 bytes off the counter; first 64 bytes: bits 0->1 33, 1->0 0
               first bytes: 00 01 02 07 04 05 0E 0F 08 09 0A 0F 1C 1D 1E 1F
```

## Статистика

```
[    60s] line 0: 1952 ans 3/s  line 1: 1952 ans 3/s (resync 2)  ...
```

Что означают счётчики:
- `ans` — отправленные ответы;
- `exc` — отправленные исключения;
- `foreign` — запросы к чужим адресам;
- `bcast` — широковещательные запросы;
- `resync` — сколько байт пропущено в поисках кадра (помехи, битый кадр);
- `drop` / `badcrc` — внесённые сбои.

## Пакет Debian

```sh
./build.sh && packaging/build-deb.sh     # dist/modbus-slave_<версия>_{amd64,arm64,armhf}.deb
```

Что ставится:
- `/usr/bin/modbus-slave` и ссылка `modbus_slave` — имя из v1;
- `modbus-slave.service` — после установки **выключен**;
- `/etc/default/modbus-slave` — параметры в `MODBUS_SLAVE_OPTS`, при обновлении пакета ваши правки сохраняются;
- профили и примеры — в `/usr/share/modbus-slave/profiles/`, скрипты для данных — в `/usr/share/modbus-slave/scripts/`.

```sh
sudoedit /etc/default/modbus-slave
sudo systemctl enable --now modbus-slave
journalctl -u modbus-slave -f
```

## v1 (C)

Версия на C лежит в `src/`, её бинарники — в `bin/` (Linux x86_64, aarch64, Windows x64). Командная строка
v2 понимает параметры v1 (`-p -b -a -o -f -t -d -k -s`). Устройство v1 — это `--profile generic`
(по умолчанию): 20 holding-регистров, FC 3 (v2 отвечает и на FC 4 по той же карте), значения случайные или
из файла.
